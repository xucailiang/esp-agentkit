# ESP Agent Kit 开发路线图

产品定位、核心特性和用户流程统一以[项目定位文档](project-positioning.md)为准。本文维护各阶段的功能设计、完成条件、勾选状态和验证记录；当前实现机制见[架构文档](architecture-and-development.md)。勾选仅表示对应条目所述范围已完成。

## 推进方式

路线图聚焦嵌入式应用开发、调试、验证和交接，不扩展为电路与 PCB、结构设计、制造或规模化设备运维平台。按代表任务逐步交付可验证的完整流程，不设定未经安排的发布日期。

当前阶段一核心改动已完成，仍有待验收事项；阶段二至五尚待开发。原生构建、调试器、通用会话协调及升级能力不能视为已经实现。

## 分阶段建设

各阶段表示建设重心，每个阶段选择代表场景交付完整流程，并继续修复已支持场景的阻碍。阶段二随原生后端提炼公共接口，阶段三、四复用其版本与操作记录；硬件适配、方案沉淀和跨系统验证可以并行开展。功能设计保持在模块与流程层面，具体命令、配置字段和内部接口在实施时确定。

### 阶段一：完善现有 MicroPython 开发闭环

**目标：** 新建或接手一个 MicroPython 项目后，能够快速试验、修改、部署、恢复并保存成果，日常迭代无需重复首配。

**功能设计与进度（2026-11-18）：** 沿用现有本地项目和 CLI，串联环境准备、设备核对、首配建项、探针与完整应用部署。项目配置与业务文件分离，部署、重启、管理连接和实物验收分别记录；交接以完整项目目录为单位。本地回归与实板验证分别说明。

- [x] **首配与项目创建衔接。** `provision.py --project-dir` 在设备验证后生成配置、应用入口和项目说明；写入前检查目标目录，保留无关文件，管理密码仅写入项目配置，Wi-Fi 密码不写入本地项目。
- [x] **项目保存失败后继续。** 区分设备配置成功与本地保存失败；`--save-project-only` 核对已配置设备后通过 LAN 建项，无需重复 USB 首配或修改网络设置。
- [x] **显式重启已安装应用。** `restart` 核对设备、启动器、部署清单和实际文件，保留重启前诊断；诊断无法保存或版本不符时拒绝复位，重启不部署本地工作副本。
- [x] **恢复结果与用户验收衔接。** 分别记录复位确认、管理重连和应用待验收状态；已提交但重启未确认的部署，可凭同设备、同清单的成功重启记录进入显式验收，未知结果和历史观察不会自动变成新版本验收。
- [x] **核心回归与交接指引。** 精简后的 31 项本地核心测试通过，覆盖建项重试、重启拒绝与诊断、会话恢复及携带历史的项目复制后修改；Skill 补齐操作、恢复与交接步骤。复制项目回归不代替跨 Agent 或跨系统实测。
- [x] **ESP12 与屏幕代表流程实测。** 在 macOS / Python 3.12、NodeMCU V3 / ESP-12F、MicroPython 1.29.0 与 MAR1441 屏幕上，验证保留网络配置的 USB 建项、LAN 建项、探针异常与超时恢复、连接占用重试、清单不符拒绝重启及启动异常诊断保留；恢复原屏幕应用后，用户确认图片、颜色和方向正常。
- [ ] **首次联网完整流程实测。** 从新的 Wi-Fi 配置开始，完成首配、自动建项、首次应用部署和用户确认；本轮建项实测沿用已有网络设置。
- [ ] **补齐故障恢复实测。** 验证网络不可用或启动延迟、存储不足、部署中断或掉电，以及应用关闭 Wi-Fi 后的 USB 恢复；本地替身测试不作为这些实板结果。
- [ ] **屏幕应用独立供电验收。** 脱离开发电脑，以独立电源冷启动并确认当前屏幕应用行为；此前 LED 独立供电验证见[验证记录](#验证记录与待办)。
- [ ] **完整项目迁移后的跨 Agent 续作实测。** 由另一种 Agent 从独立目录中的完整项目核对现场、修改业务逻辑、部署并取得新版本观察；此前同工作区素材修改不代替这条验证。
- [ ] **Windows / Linux 验证。** 在对应系统完成环境准备、设备访问和代表开发流程；编码与路径回归不代替原生系统验证。
- [ ] **第二块板的开发闭环。** 选择一块明确的 ESP32 开发板，验证 MicroPython 首配、部署、观察和恢复，记录与 ESP8266 的差异；板型资料和芯片识别不作为通过依据。

**完成条件：** 在记录清楚的板型、系统和 Agent 组合上，新建与已有项目均完成修改、实物复测和保存；代表性失败有可执行、经过验证的恢复路径，并取得首次上手与日常迭代的实际操作负担记录。

本轮实板验证摘要见[测试说明](../tests/README.md#focused-real-board-checks)，具体操作方法见 [Skill](../skill/esp-agentkit/SKILL.md)。源码快照、部署清单、带时间的操作结果与用户确认保留在私有设备项目中。

### 阶段二：打通原生工程路径

**目标：** 接手已有 ESP-IDF 工程，或创建包含多个组件、多个任务及可控故障的应用，通过同一项目流程完成构建、烧录、观察和修改。外设与测量条件按实际硬件选择。

**功能设计：**

- [ ] **已有工程接入。** 识别工程结构、组件、配置和资源，保留原生目录、构建方式与人工接管入口；Agent 可以按需接入构建、部署或诊断，无需先迁移整个工程。
- [ ] **项目、目标与后端模型。** 随 MicroPython 和 ESP-IDF 两条实际路径分开工程类型、稳定设备身份、连接端点、载板与接线，并记录来源和确认状态。公共核心统一能力、产物与操作结果，后端保留各自的运行和恢复语义；旧项目继续可读，IPv4、WebREPL 密码不再是所有后端的共同要求。
- [ ] **环境与依赖重建。** 复用 ESP-IDF 的 SDK、工具链、组件和配置管理，记录精确版本与有效输入；桌面工具环境与工程构建环境分开，缺工具、依赖失败和编译错误提供可定位的诊断。
- [ ] **构建与产物归档。** 关联源码、配置、依赖和构建实例，保存 BIN、ELF、MAP、必要镜像与烧录布局；包含参与构建的未提交修改、本地组件和生成资源来源。部署使用确定的归档产物，源码版本、部署实例和实际运行版本分别记录。
- [ ] **USB 烧录与连续日志。** 核对目标和写入范围，区分应用更新与完整镜像写入；接入连续串口输出、启动证据和受控故障修复。基本构建、烧录与观察不统一要求设备安装常驻管理程序。
- [ ] **会话与操作协调。** 操作声明资源占用、暂停、复位、擦写范围和恢复方式；加入本机跨进程资源锁、子进程管理及取消处理，协调烧录与监控。取消或释放接口后，设备状态未经核对仍保留未知。

**完成条件：** 首先在一块明确的 ESP32、固定 ESP-IDF 版本和主机环境上完成“接手工程 → 重建环境 → 构建归档 → 核对并经 USB 烧录 → 观测并确认运行版本 → 定位受控故障 → 修复重烧 → 独立供电验证 → 换 Agent 续作”。修复按原条件复测并保存用户观察，已有 MicroPython 核心回归继续通过。可重建环境与产物逐字节一致分别验证，新系统、新板型及更深的调试能力另行验证。

设计依据：[ESP-IDF 构建系统](https://docs.espressif.com/projects/esp-idf/en/stable/esp32/api-guides/build-system.html) · [依赖锁定](https://docs.espressif.com/projects/idf-component-manager/en/latest/reference/dependencies_lock.html) · [可复现构建](https://docs.espressif.com/projects/esp-idf/en/stable/esp32/api-guides/reproducible-builds.html)。

### 阶段三：覆盖复杂调试与验证

**目标：** 支持多外设、多任务应用中偶发故障与性能问题的定位，并用相同条件验证修复结果。

**功能设计：**

- [ ] **持续观测。** 接入日志、任务、内存及必要运行指标，关联实际运行版本、时间来源和采集条件；尽量避免暂停应用，记录采集开销与数据丢失。
- [ ] **交互调试。** 按芯片、载板和接口条件接入 OpenOCD/GDB 等成熟工具，支持断点、单步、变量和任务观察，明确暂停、恢复及调试器占用的影响。
- [ ] **崩溃诊断。** 保存原始崩溃信息和转储，使用实际运行版本对应的 ELF 解析调用栈与位置；版本无法匹配时明确限制，诊断结果回到对应项目和构建记录。
- [ ] **资源约束验证。** 把响应时间、采样周期、内存余量、时序和功耗要求转成可测条件，结合板端指标及逻辑分析仪、电流测量等必要外部证据；断点测试不代替实时性能测量。
- [ ] **场景测试与故障注入。** 建立本地可复现的实板检查，覆盖模块协作、资源冲突、断连、取消和启动失败；保存条件、结果及版本，按核心流程组织回归，避免逐参数扩张测试。

**完成条件：** 对代表性的多外设、多任务故障完成复现、定位、修复和原条件复测，性能结论有测量依据，失败与恢复状态可解释。仅在持续会话确有需要时引入轻量管理进程。

设计依据：[ESP-IDF 调试](https://docs.espressif.com/projects/esp-idf/en/stable/esp32/api-guides/jtag-debugging/debugging-examples.html) · [运行追踪](https://docs.espressif.com/projects/esp-idf/en/stable/esp32/api-guides/tracing/index.html) · [崩溃转储](https://docs.espressif.com/projects/esp-idf/en/stable/esp32/api-guides/core_dump.html)。

### 阶段四：完善交付与升级维护

**目标：** 项目能够脱离开发会话持续使用，后续更新保留必要数据，失败后有明确的恢复办法。

**功能设计：**

- [ ] **交付与长期运行。** 整理源码、依赖、配置、接线、版本和未解决问题，核对设备实际运行版本；验证独立供电冷启动及约定运行条件，记录执行器在暂停、复位和失联时的实际状态。
- [ ] **更新范围与业务数据。** 分开处理脚本包、应用镜像、完整固件、启动程序、分区及业务数据，提前说明写入影响；设计数据保留、格式迁移和旧版本兼容规则。
- [ ] **健康确认与恢复。** 按后端能力接入应用健康检查、OTA 和回滚，明确何时确认新版本、何时退出更新及如何人工恢复。MicroPython 保留完整重部署路径，原生 OTA 核对分区和启动程序条件。
- [ ] **升级失败验证。** 在可恢复的测试设备上验证传输中断、掉电、启动失败和数据迁移失败，分别记录程序可用性、数据完整性及恢复结果。
- [ ] **联网维护与凭据管理。** 按实际使用场景补充认证、加密、签名和密钥管理，敏感配置与私钥不进入通用快照或公开回执；不可逆设备配置单独说明影响与授权。

**完成条件：** 在具体项目上证明独立运行、更新成功、失败恢复和业务数据兼容；管理重连或文件写入成功不能代替应用健康与用户验收。不以建设规模化设备管理平台作为本阶段前提。

设计依据：[ESP-IDF OTA 与回滚](https://docs.espressif.com/projects/esp-idf/en/stable/esp32/api-reference/system/ota.html)。

### 阶段五：扩展硬件与方案复用

**目标：** 将经过验证的开发流程推广到更多硬件、工程类型和开发环境，减少重复适配与项目重建。

**功能设计：**

- [ ] **可查询的能力与适配约定。** 后端分别声明发现、身份确认、配置、编程、运行、观测和恢复能力，区分后端支持、硬件条件和当前连接已验证状态，附实际板型、固件、系统与工具版本组合。
- [ ] **新硬件与开发环境。** 按项目需求接入更多 ESP 板型、Arduino/PlatformIO 及其他 MCU 或 Linux 设备；候选包括 picotool、STM32CubeProgrammer 和 SSH。复用成熟工具与原生工程格式，识别按协议复用，接线与资源差异保存在板型及设备项目中；先完成真实开发路径，再提炼公共接口。
- [ ] **外设与应用方案。** 复用 GPIO、I²C、SPI、UART 等接口与现有驱动，沉淀组件、模板、接线和故障恢复方案，注明依赖版本、资源条件、许可证及验证范围；确有原生库或时序需求时再接入 C 绑定和定制固件，保留原生源码维护方式。
- [ ] **跨环境接手。** 将项目、环境说明和操作记录作为可迁移单元，在不同电脑、系统及 Agent 上重建环境、核对现场并继续修改；必要的兼容处理进入公共工具，保持基础路径独立于专属插件。
- [ ] **适配验证与贡献流程。** 提供可在本地执行的后端验证约定，以完整任务验证新增能力，并检查已有路径是否受影响；共享适配和方案保留来源、版本及维护条件，社区贡献沿用同一标准。

**完成条件：** 新后端通过身份、编程、运行、观测和恢复验证，方案能在不同项目或环境中复用，并有开发负担变化的实测记录。公网访问和多设备管理不作为本轮硬件扩展的交付目标。

## 效果衡量

每阶段选择代表任务，对比“通用 Agent＋现有底层工具”和“Agent＋ESP Agent Kit”的首次完成率、耗时、用户介入次数、故障恢复结果及续作准确性。记录开发者经验、硬件、系统、Agent 和任务条件，无法公平对比时只记录本次结果，不宣称效率提升。新增命令、后端和板型数量不能替代开发便利性与可靠性的验证。

实现与验证遵循 [AGENTS.md](../AGENTS.md) 中的开发、基础设施和发布约束；依赖版本与许可证统一维护在[第三方软件清单](third-party.md)。

## 验证记录与待办

本节保存实测事实及对应验证边界，阶段任务状态见[分阶段建设](#分阶段建设)。每次验证注明所用硬件和实际覆盖范围。当前实测使用 NodeMCU V3 / ESP-12F（ESP8266EX，4 MiB），已通过板载 LED 和 MAR1441 128×128 SPI 屏幕观察程序行为。

2026-11-18，统一检测入口完成一次实板识别：`--list` 返回一个 CH340 USB 串口及两个非 USB 串口；默认 `detect` 自动选择唯一 USB 候选，识别出 ESP8266EX，Flash ID 为 `0x164020`、容量为 4,194,304 字节，退出码为 0、无警告，正常复位请求已发送。检测结果保留未知载板及未检查的运行能力，没有据此推断固件或部署兼容性。

检测仍待实板确认：`--list` 期间的应用连续行为、多个候选时的端口选择，以及探测后的应用正常启动。还需用一块未在 `boards/` 登记、且 esptool 支持的载板验证无需新增中央板型文件即可识别。自动检测通过后仍需独立验证首配和部署兼容性。
